# APIs: endpoint lento no backend

## Resumo

Primeiro **medir** para descobrir onde o tempo é gasto; depois **corrigir a causa** encontrada; por fim **medir de novo** para confirmar o ganho. Otimizar sem medir costuma resolver o problema errado.

## 1. Identificar

1. **Reproduzir e medir o tempo total.** Chamar o endpoint com os mesmos parâmetros (curl, Postman, navegador) e anotar o tempo de resposta e o tamanho do payload. Verificar se a lentidão é constante ou só com certos dados, horários ou volume.
2. **Contar e medir as consultas SQL.** Laravel Telescope, Debugbar ou `DB::listen()` mostram quantas queries foram executadas e quanto cada uma levou. Muitas queries iguais indicam **N+1**; poucas queries lentas indicam **falta de índice** ou consulta mal escrita.
3. **Analisar as queries lentas.** `EXPLAIN` no MySQL mostra se a consulta usa índice ou faz varredura completa da tabela (`type: ALL`), e quantas linhas são examinadas. O *slow query log* do MySQL/RDS revela as consultas mais pesadas em produção.
4. **Rastrear o restante do tempo.** Ferramentas de APM (New Relic, Datadog, Sentry Performance, Laravel Nightwatch/Pulse) quebram o tempo por etapa: banco, cache, chamadas HTTP externas, serialização, filas.
5. **Olhar a infraestrutura.** CPU, memória e conexões do servidor e do banco; tempo de resposta de serviços externos; limites de conexão.

## 2. Causas comuns e soluções

| Causa | Como aparece | Solução |
|---|---|---|
| **N+1 queries** | Dezenas de consultas iguais variando só o id | Eager loading com `with()`/`load()`; `Model::preventLazyLoading()` em desenvolvimento para detectar |
| **Falta de índice** | `EXPLAIN` com varredura completa | Índices nas colunas de `WHERE`, `JOIN` e `ORDER BY`; índices compostos na ordem certa |
| **Dados demais** | Payload grande, muitas colunas | Paginação, `select()` só das colunas necessárias, API Resources enxutos |
| **Processamento repetido** | O mesmo cálculo a cada requisição | Cache (Redis/Memcached) com expiração e invalidação quando o dado muda |
| **Serviço externo lento** | Tempo alto em chamadas HTTP | Timeout, cache da resposta, ou mover para **fila** e responder de forma assíncrona |
| **Tarefa pesada na requisição** | Envio de e-mail, geração de PDF, processamento de imagem | Jobs em fila (ver Ex. 07) |
| **Agregações caras** | `SUM`/`COUNT` sobre tabelas grandes a cada chamada | Tabelas de resumo atualizadas por job/evento, ou réplica de leitura |
| **Configuração** | Tempo alto mesmo em rotas simples | `config:cache`, `route:cache`, OPcache, autoload otimizado, PHP atualizado |

## 3. Validar

- Medir novamente com o mesmo cenário e comparar com o número inicial.
- Criar um teste que falhe se o número de queries voltar a crescer.
- Monitorar em produção (percentis p95/p99, não só a média) para garantir que a melhora se mantém com carga real.

## No código deste projeto

- `AppServiceProvider` ativa `Model::preventLazyLoading()` fora de produção: um N+1 vira erro durante o desenvolvimento, antes de chegar ao usuário.
- `GET /api/produtos` é **paginado** (padrão 12, máximo 50 por página).
- `ProdutoResource` devolve apenas os campos necessários ao frontend.
