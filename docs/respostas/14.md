# SQL com Eloquent: clientes e pedidos

## Estrutura considerada

```php
class Cliente extends Model
{
    protected $table = 'clientes';

    public function pedidos(): HasMany
    {
        return $this->hasMany(Pedido::class, 'cliente_id');
    }
}

class Pedido extends Model
{
    protected $table = 'pedidos';

    public function cliente(): BelongsTo
    {
        return $this->belongsTo(Cliente::class, 'cliente_id');
    }
}
```

## 1. Estados com o maior volume de vendas (soma de `valor_total`)

```php
$estados = Pedido::query()
    ->join('clientes', 'clientes.id', '=', 'pedidos.cliente_id')
    ->select('clientes.estado')
    ->selectRaw('SUM(pedidos.valor_total) AS volume_vendas')
    ->selectRaw('COUNT(pedidos.id) AS quantidade_pedidos')
    ->groupBy('clientes.estado')
    ->orderByDesc('volume_vendas')
    ->get();
```

SQL gerado:

```sql
SELECT clientes.estado,
       SUM(pedidos.valor_total) AS volume_vendas,
       COUNT(pedidos.id) AS quantidade_pedidos
FROM pedidos
INNER JOIN clientes ON clientes.id = pedidos.cliente_id
GROUP BY clientes.estado
ORDER BY volume_vendas DESC;
```

- O `JOIN` parte de `pedidos`: estados sem nenhum pedido não aparecem (não têm volume).
- A contagem de pedidos vem junto, sem custo extra, e ajuda a analisar ticket médio por estado.
- Para "os N estados de maior volume", basta acrescentar `->limit(N)`.

## 2. Os 5 clientes que mais compraram (considerando `valor_total`)

```php
$melhoresClientes = Cliente::query()
    ->join('pedidos', 'pedidos.cliente_id', '=', 'clientes.id')
    ->select('clientes.id', 'clientes.nome', 'clientes.email', 'clientes.estado')
    ->selectRaw('SUM(pedidos.valor_total) AS total_comprado')
    ->groupBy('clientes.id', 'clientes.nome', 'clientes.email', 'clientes.estado')
    ->orderByDesc('total_comprado')
    ->limit(5)
    ->get();
```

Alternativa mais "Eloquent", com o relacionamento:

```php
$melhoresClientes = Cliente::query()
    ->withSum('pedidos as total_comprado', 'valor_total')
    ->orderByDesc('total_comprado')
    ->limit(5)
    ->get();
```

- As duas dão o mesmo resultado. `withSum` é mais legível, mas gera uma **subconsulta correlacionada** para cada cliente; em tabelas grandes, o `JOIN` + `GROUP BY` costuma ser mais eficiente.
- Todas as colunas não agregadas estão no `GROUP BY`, compatível com o modo `ONLY_FULL_GROUP_BY` do MySQL.
- Em caso de empate na 5ª posição, um segundo critério (`->orderBy('clientes.id')`) torna o resultado determinístico.

## 3. Como otimizar essas consultas

**Índices**

```sql
CREATE INDEX idx_pedidos_cliente_valor ON pedidos (cliente_id, valor_total);
CREATE INDEX idx_clientes_estado ON clientes (estado);
```

- `pedidos(cliente_id, valor_total)` é um **índice de cobertura**: o MySQL faz o join e a soma lendo só o índice, sem acessar as linhas da tabela.
- A FK `cliente_id` já cria um índice simples no InnoDB; o composto o substitui com vantagem.
- Se as consultas forem filtradas por período (o caso mais comum em relatórios), incluir `data_pedido`: `pedidos(data_pedido, cliente_id, valor_total)`.
- Conferir com `EXPLAIN` que os índices estão sendo usados.

**Evitar recalcular a cada acesso**

- **Cache** do resultado (Redis/Memcached, ver Ex. 05) com expiração, invalidado quando entra um pedido novo. Rankings e relatórios toleram alguns minutos de atraso.
- **Tabela de resumo** (por exemplo `vendas_por_estado` e `vendas_por_cliente`) atualizada por um job agendado ou por evento a cada pedido pago. A consulta vira uma leitura simples, em vez de somar milhões de linhas.
- **Réplica de leitura** do RDS para relatórios, sem disputar recursos com as vendas.

**No Eloquent**

- Selecionar só as colunas necessárias e usar `toBase()` quando não for preciso hidratar models (menos memória e CPU).
- Para exportações grandes, `chunk()`/`lazy()` em vez de `get()`.
- Com volume muito alto, **particionar** `pedidos` por período.
