# Crítica de código: transformer de item de pedido

## Problemas encontrados

1. **Chamadas repetidas aos relacionamentos.** `getProduct()` é chamado **4 vezes** e `getSize()` **3 vezes**. Dependendo da implementação, cada chamada pode disparar uma consulta ao banco (ou pelo menos refazer o mesmo trabalho). Em uma lista de 50 itens, isso pode virar centenas de consultas, o mesmo padrão do **N+1** (Ex. 06).
2. **Nenhum tratamento de nulo.** Se o produto foi excluído ou desativado, ou se o item não tem tamanho (acessório, por exemplo), `getProduct()` ou `getSize()` devolvem `null` e a chamada seguinte gera **erro fatal** ("Call to a member function … on null"), derrubando a resposta inteira. É exatamente o erro do log do Ex. 09.
3. **Responsabilidades misturadas.** O transformer do item também formata o produto e o tamanho por dentro. Isso duplica lógica que provavelmente já existe em um `ProductTransformer`/`SizeTransformer` e obriga o cliente a receber sempre todos esses campos.
4. **Nomes inconsistentes.** `item_pedido_id` em português e o restante em inglês (`product_id`, `quantity`…). A API fica imprevisível para quem consome.
5. **Sem tipo de retorno** (`: array`) e dependência de o controller ter feito o *eager loading* correto, sem garantia.
6. **Valores monetários sem padrão definido** (float? centavos? string formatada?), o que costuma gerar diferenças de arredondamento entre backend e frontend.

## Versão melhorada

```php
/**
 * Transforma um item de pedido em array para a API. Produto e tamanho são
 * lidos uma única vez e podem ser nulos (produto removido, item sem tamanho).
 */
public function transform(InterfaceItemPedido $itemPedido): array
{
    $produto = $itemPedido->getProduct();
    $tamanho = $itemPedido->getSize();

    return [
        'item_pedido_id' => $itemPedido->getId(),
        'produto_id' => $itemPedido->getProductId(),
        'quantidade' => $itemPedido->getQuantity(),
        'preco' => $itemPedido->getPrice(),
        'preco_total' => $itemPedido->getTotalPrice(),
        'desconto' => $itemPedido->getDiscount(),
        'produto_nome' => $produto?->getName(),
        'link_rewrite' => $produto?->getLinkRewrite(),
        'produto_ativo' => $produto?->isActive() ?? false,
        'produto_tipo' => $produto?->getType(),
        'tamanho_nome' => $tamanho?->getName(),
        'genero' => $tamanho?->getGender(),
        'genero_nome' => $tamanho?->getLongGender(),
    ];
}
```

O que mudou:

- Produto e tamanho são obtidos **uma vez** e reutilizados.
- **Operador null-safe** (`?->`, PHP 8): se o relacionamento não existir, o campo vem `null` em vez de derrubar a resposta.
- `produto_ativo` tem valor padrão (`false`) quando o produto não existe.
- Tipo de retorno `array` e nomes de chave em um único idioma. Em uma API já publicada, a troca de nomes precisa de versionamento (v2) ou período de transição para não quebrar clientes.

## Melhorias além do método

- **Includes do Fractal** (`includeProduto`, `includeTamanho`) com os transformers próprios: o cliente pede `?include=produto,tamanho` só quando precisa, e a formatação do produto fica em um lugar só.
- **Eager loading no controller/repositório**: `ItemPedido::with(['product', 'size'])`, garantindo 2 consultas para a lista inteira em vez de uma por item.
- **Dinheiro em centavos (inteiro)** ou string decimal padronizada, evitando erros de ponto flutuante.
- **Testes** do transformer com item sem produto e sem tamanho.
