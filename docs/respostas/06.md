# Eloquent: vantagens, desvantagens e N+1

## Vantagens

- **Produtividade e legibilidade:** cada tabela vira uma classe (`Produto::where(...)->get()`), com relacionamentos declarados (`hasMany`, `belongsTo`) e consultas encadeadas que se leem quase como texto.
- **Segurança:** o Query Builder usa *prepared statements*, o que evita SQL injection nas consultas comuns. `$fillable` protege contra atribuição em massa indevida.
- **Recursos prontos:** casts (`decimal:2`, `hashed`, datas), escopos, eventos e observers, soft deletes, paginação, factories e seeders integrados.
- **Independência de banco:** a mesma consulta funciona em MySQL, PostgreSQL ou SQLite (os testes deste projeto rodam em SQLite em memória, e a aplicação em MySQL).
- **Integração com o ecossistema:** API Resources, validação com `exists`/`unique`, route model binding (`Produto $produto` no controller).

## Desvantagens

- **Esconde o SQL:** fica fácil escrever código que gera consultas ruins sem perceber, principalmente o **N+1**.
- **Custo de hidratação:** cada linha vira um objeto com atributos, casts e eventos. Para relatórios com milhares de linhas, isso consome memória e CPU.
- **Consultas complexas:** agregações, subconsultas e *window functions* ficam verbosas; às vezes o SQL direto é mais claro.
- **Active Record acopla** a regra de negócio ao banco; models grandes viram "classes Deus" se não houver disciplina (services, actions).

## O problema N+1

Acontece quando se busca uma lista (1 consulta) e depois se acessa um relacionamento de cada item, gerando **uma consulta a mais para cada item** (N consultas).

```php
$pedidos = Pedido::all();

foreach ($pedidos as $pedido) {
    echo $pedido->cliente->nome;
}
```

Com 100 pedidos: 1 consulta para os pedidos + 100 consultas para os clientes = **101 consultas**.

### Correção: eager loading

```php
$pedidos = Pedido::with('cliente')->get();
```

Agora são **2 consultas**: uma para os pedidos e uma para todos os clientes envolvidos (`WHERE id IN (...)`).

Outras ferramentas:

- `load()` / `loadMissing()` para carregar depois de já ter a coleção.
- `withCount()`, `withSum()` para contagens e somas sem carregar os registros.
- `Model::preventLazyLoading()` em desenvolvimento: qualquer acesso preguiçoso lança exceção, e o N+1 é descoberto antes de ir para produção.
- Telescope/Debugbar para contar consultas por requisição.

## Quando sair do Eloquent

- Relatórios e agregações pesadas: Query Builder (`DB::table()`) ou `toBase()`, que devolvem objetos simples, sem hidratar models.
- Processamento de milhões de linhas: `chunk()`, `lazy()` ou `cursor()` para não carregar tudo na memória.
- Consultas muito específicas do banco: SQL direto com `DB::select()` e *bindings*.

## No código deste projeto

`backend/app/Providers/AppServiceProvider.php` ativa `Model::preventLazyLoading(! $this->app->isProduction())`, ou seja, qualquer N+1 quebra o desenvolvimento e os testes, mas não derruba a produção.
