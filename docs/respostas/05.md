# Memcached / ElastiCache com Laravel e MySQL (RDS)

## Resumo

O banco relacional (MySQL no RDS) é o recurso mais caro e mais difícil de escalar da aplicação. Um cache em memória, como **Memcached** ou **Redis**, gerenciados pela AWS no **ElastiCache**, guarda resultados que são lidos muitas vezes e mudam pouco. As leituras passam a ser feitas em memória, em microssegundos, e o banco recebe só o que realmente precisa dele.

## Por que usar

1. **Tira carga do banco.** Catálogo de produtos, categorias, configurações, páginas de produto e resultados de consultas agregadas são lidos milhares de vezes e raramente mudam. Com cache, só a primeira leitura vai ao MySQL.
2. **Respostas mais rápidas.** Ler da memória é muito mais rápido do que executar uma consulta com `JOIN` e `ORDER BY` no disco.
3. **Custo.** Escalar o RDS verticalmente (instância maior) ou com réplicas é caro. Um nó de cache pequeno costuma absorver a maior parte das leituras repetidas.
4. **Sessões e dados temporários.** Com vários servidores de aplicação, sessões, rate limiting e locks precisam estar num lugar compartilhado. O cache centralizado resolve isso sem sobrecarregar o banco.

## Como ajuda na escalabilidade

- **Escala horizontal da aplicação:** os servidores PHP ficam *stateless*; qualquer um atende qualquer requisição, porque sessão e cache estão no ElastiCache. Dá para adicionar instâncias atrás do load balancer conforme a demanda.
- **O banco deixa de ser gargalo:** com a maior parte das leituras servidas pelo cache, o RDS suporta mais usuários com a mesma instância, e as réplicas de leitura ficam para consultas que não podem ser cacheadas.
- **O próprio cache escala:** o Memcached distribui chaves entre vários nós; o Redis no ElastiCache oferece réplicas, *cluster mode* e failover automático.

## Memcached × Redis

| | Memcached | Redis |
|---|---|---|
| Modelo | Chave/valor simples, multi-thread | Estruturas de dados (listas, sets, hashes, sorted sets) |
| Persistência e replicação | Não | Sim (réplicas, failover, snapshots) |
| Uso no Laravel | Cache e sessão | Cache, sessão, **filas**, locks, rate limiting, broadcasting |
| Quando escolher | Cache puro, simples e volumoso | Quando o cache também sustenta filas, locks ou precisa sobreviver a falhas |

## No Laravel

```php
$produtos = Cache::remember('vitrine:camisetas:pagina:1', now()->addMinutes(10), function () {
    return Produto::where('nome', 'like', 'Camiseta%')->latest()->paginate(12);
});
```

- Configuração: `CACHE_STORE=memcached` (ou `redis`) e `SESSION_DRIVER` apontando para o mesmo serviço.
- **Invalidação** é a parte difícil: usar TTL, apagar a chave quando o dado muda (observers/eventos do model) ou **tags** de cache no Redis (`Cache::tags(['produtos'])->flush()`).
- Evitar `rememberForever` para dados que mudam: sem expiração e sem invalidação, o cache serve dado desatualizado indefinidamente (o log do Ex. 09 usa `rememberForever`).
- Proteger contra *cache stampede* (muitas requisições recalculando a mesma chave ao mesmo tempo) com `Cache::lock()` ou `Cache::flexible()`.
