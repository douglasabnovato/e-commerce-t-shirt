# Transactions

## Resumo

Uma **transaction** agrupa várias operações no banco em uma unidade **atômica**: ou todas são gravadas, ou nenhuma é. Se algo falha no meio, o banco desfaz tudo (*rollback*) e os dados continuam consistentes.

## Quando é interessante usar

1. **Operações que precisam acontecer juntas.** Criar um pedido envolve: gravar o pedido, gravar os itens, baixar o estoque e registrar o pagamento. Se a baixa de estoque falhar depois de o pedido ter sido criado, o sistema ficaria com um pedido sem reserva de produto.
2. **Transferências e saldos.** Debitar de uma conta e creditar em outra; um sem o outro gera dinheiro "sumido" ou "criado".
3. **Concorrência sobre o mesmo registro.** Dois clientes comprando a última unidade ao mesmo tempo. Dentro da transaction, `lockForUpdate()` trava a linha do estoque até o fim, e só um deles consegue.
4. **Registros dependentes.** Criar um usuário e o perfil dele, um produto e suas variações, ou apagar um registro e seus filhos.
5. **Importações e atualizações em lote,** quando uma planilha deve entrar inteira ou não entrar.

## No Laravel

```php
$pedido = DB::transaction(function () use ($dados, $itens) {
    $pedido = Pedido::create($dados);

    foreach ($itens as $item) {
        $estoque = Estoque::where('produto_id', $item['produto_id'])->lockForUpdate()->firstOrFail();

        if ($estoque->quantidade < $item['quantidade']) {
            throw new EstoqueInsuficienteException($item['produto_id']);
        }

        $estoque->decrement('quantidade', $item['quantidade']);
        $pedido->itens()->create($item);
    }

    return $pedido;
}, attempts: 3);
```

- Qualquer exceção dentro da closure faz o **rollback** automático.
- `attempts` repete a transaction em caso de *deadlock*.

## Cuidados

- **Transactions curtas:** enquanto estão abertas, seguram locks e travam outras requisições.
- **Nada externo lá dentro:** chamadas a APIs, envio de e-mail ou gravação de arquivos não são desfeitas pelo rollback. Devem acontecer **depois do commit** (`DB::afterCommit()`, eventos com `ShouldDispatchAfterCommit`, ou jobs despachados com `afterCommit()`).
- **Leituras simples não precisam** de transaction.
- O banco precisa suportar (InnoDB no MySQL suporta; MyISAM não).

## Relação com este projeto

No CRUD do Ex. 10 há uma única escrita por operação, então uma transaction não seria necessária. O problema parecido que existe é a consistência entre **banco e disco**: se a gravação do produto falhar depois do upload, a imagem ficaria órfã. O `ProdutoController` trata isso **compensando** a operação (apaga a imagem recém-enviada no `catch`), porque o rollback do banco não desfaz arquivos.
