# Laravel + Vue.js: autenticação entre frontend e backend

## Resumo

Quando o frontend Vue e a API Laravel estão no **mesmo domínio** (ou subdomínios do mesmo domínio), a abordagem mais segura é o **Laravel Sanctum em modo SPA**: autenticação por **sessão**, com o identificador guardado em **cookie HttpOnly** e proteção contra **CSRF**. O JavaScript nunca tem acesso à credencial.

Tokens (Bearer) ficam para clientes que não são o próprio frontend web: aplicativos mobile, integrações entre sistemas, APIs públicas.

Esta é a estratégia implementada no Ex. 10 deste projeto.

## Onde guardar a credencial: comparação

| Opção | Risco principal | Quando usar |
|---|---|---|
| `localStorage` / `sessionStorage` | Qualquer script injetado (XSS) lê o token e o envia para fora. O token continua válido fora do navegador. | Evitar para credenciais |
| Token só em memória (variável JS) | Some ao recarregar a página; ainda exposto a XSS enquanto a página está aberta | Tokens de curta duração, com renovação |
| **Cookie HttpOnly + Secure + SameSite** | JavaScript não lê o cookie; o risco passa a ser CSRF, que o Laravel trata | **SPA no mesmo domínio (escolhido)** |
| Bearer token em app nativo | Armazenamento seguro do sistema (Keychain/Keystore) | Mobile e integrações |

## Fluxo seguro de login (como foi implementado)

1. **Cookie CSRF.** O Vue chama `GET /sanctum/csrf-cookie`. O Laravel devolve o cookie `XSRF-TOKEN`.
2. **Login.** O Vue envia `POST /api/login` com e-mail e senha. O axios copia automaticamente o valor do cookie para o cabeçalho `X-XSRF-TOKEN`. O Laravel confere o CSRF e as credenciais (`Auth::attempt`).
3. **Sessão.** Com sucesso, o Laravel **regenera o id da sessão** (evita *session fixation*) e devolve o cookie de sessão **HttpOnly**. A resposta traz apenas dados públicos do usuário (id, nome, e-mail).
4. **Requisições seguintes.** O navegador envia o cookie sozinho. Rotas protegidas usam o middleware `auth:sanctum`. Sem sessão válida, a API responde **401**.
5. **Estado no Vue.** O Pinia guarda só os dados públicos do usuário. Ao abrir a aplicação, `GET /api/user` informa se já existe sessão. O router bloqueia as páginas de administração para quem não está logado.
6. **Logout.** `POST /api/logout` encerra a sessão, invalida o id e gera um novo token CSRF.

## Comunicação entre as camadas

- **HTTPS obrigatório** em produção, com cookies `Secure`.
- **Mesma origem:** em desenvolvimento o Vite faz proxy de `/api` e `/sanctum` para o Laravel; em produção o Laravel serve a API e o build do Vue no mesmo domínio. Assim não há CORS com credenciais para configurar.
- Se front e API estivessem em subdomínios diferentes: `SANCTUM_STATEFUL_DOMAINS`, `SESSION_DOMAIN` e CORS com `supports_credentials`.
- **Validação sempre no backend** (Form Requests), mesmo que o front também valide.
- **Autorização além da autenticação:** policies/gates quando houver perfis diferentes.

## Proteções complementares

- **Limite de tentativas de login** (5 por minuto por e-mail e IP) contra força bruta.
- **Mensagem genérica** em credenciais inválidas ("E-mail ou senha inválidos"), sem revelar se o e-mail existe.
- **Senhas com hash** (bcrypt, via cast `hashed` do Laravel).
- **Content Security Policy** e escape de conteúdo para reduzir o risco de XSS.
- **Expiração de sessão** configurável (`SESSION_LIFETIME`).

## No código deste projeto

- `backend/bootstrap/app.php`: `statefulApi()` ativa o modo SPA do Sanctum.
- `backend/app/Http/Controllers/Api/AuthController.php`: login, usuário atual e logout.
- `backend/app/Providers/AppServiceProvider.php`: limite de tentativas de login.
- `frontend/src/services/api.js` e `frontend/src/stores/autenticacao.js`: CSRF, envio de cookies e estado do usuário.
- `backend/tests/Feature/AutenticacaoTest.php`: testes de login, senha errada, bloqueio por tentativas, 401 e logout.
